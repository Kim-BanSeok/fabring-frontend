# 구매자 픽업 예약 API 연동

2026-10-12 KST · 백엔드 기준 `7dc28c79994295daee635524d05048574247a6d9`

실제 계정 모드의 구매자 픽업 요청·내 예약 목록·상세·취소를 기존 예약 API에 연결했습니다. 기존 배치와 요청 → 접수 → 내역 → 취소 확인 흐름을 유지했습니다. **프론트 테스트148개·lint·빌드, 로컬 HTTP87개와 아래 브라우저 검증을 완료했습니다.**

백엔드 main을 다시 확인했으며 직전 원단 조회 연동 기준 `7dc28c7` 이후 추가 커밋은 없었습니다. 기존 [원단 조회 QA](../fabric-api-2026-10-12/README.md)와 [인증 QA](../auth-api-2026-10-11/README.md)는 당시 범위와 결과를 보존합니다. 과거 기록의 “예약 미연동”은 해당 검증 시점의 상태입니다.

## 연결 범위

기본 주소는 `/api/v1`, 성공 응답은 `{ success: true, data }`입니다. 이번 작업은 아래 네 API의 구매자 동선을 연결합니다.

| API | 화면·동작 | 서버 응답 |
| --- | --- | --- |
| 25 `POST /reservations` | 원단 확인 후 픽업 요청 | 201, `reservationId`, `status=REQUESTED`, `estimated_price` |
| 26 `GET /reservations/me` | 내 예약 목록·상태 탭·페이지 이동 | `content`, `page`, `size`, `totalElements`, `totalPages` |
| 28 `GET /reservations/{reservationId}` | 예약 상세·접수 결과·취소 전 확인 | 예약 정보, 원단 요약, 현재 매장 정보 |
| 31 `POST /reservations/{reservationId}/cancel` | 구매자가 본인의 요청됨·수락됨 예약 취소 | 200, `reservationId`, `status=CANCELED` |

로그인한 BUYER만 요청·내 목록을 이용합니다. 상세·취소는 해당 예약의 구매자 또는 판매자에게 허용되지만 이번 화면 연결은 구매자만 대상으로 합니다. ADMIN에게 예약 상세 권한이 자동으로 생기지 않습니다. 잘못되거나 만료된 인증은 기존 세션 만료 흐름으로 처리합니다.

원단 목록·상세는 기존 실제 조회를 유지하고, 예약 화면의 조회 실패·빈 내역을 시연 데이터로 대체하지 않습니다. 시연 모드의 예약은 실제 계정·API 동작과 분리합니다.

판매자 받은 예약 목록27·수락29·거절30·수령32·판매자 취소31은 이번 프론트 범위 밖입니다. 해당 서버 기능은 이미 존재하므로 서버 신규 구현이 필요한 것으로 표시하지 않습니다. 문의·프로필 수정·원단 등록·관리자 처리 등 다른 미연동 기능도 별도입니다. 추천·도안 서비스와 연결되지 않은 화면의 예시 도안명을 실제 `pattern_id`로 보내지 않습니다.

## 요청과 상태 전환

- 생성 요청은 숫자 `fabric_id`, `pickup_at`이 필수입니다. `memo`는 trim 후 최대500자이며 빈 값은 null로 보낼 수 있습니다. `pattern_id`는 선택이며 실제 사용 중인 도안 번호만 허용됩니다.
- 자투리는 한 장 전체를 요청하므로 `requested_length_cm`을 생략하거나 null로 보냅니다. 롤은 숫자 길이를 필수로 보내며 90cm의 양의 배수여야 합니다. 현재 구매 가능 길이 안에서 입력해도 전송 시점에는 재고가 달라질 수 있습니다.
- 요청 성공은 REQUESTED이며 재고 확보·방문 확정이 아닙니다. 판매자 수락 시 재고를 확보하고 픽업 일시를 조정할 수 있습니다. 프론트가 요청 직후 ACCEPTED로 바꾸거나 재고를 임의로 차감하지 않습니다.
- 생성 응답은 예약번호·상태·예상금액만 제공합니다. 전체 상세가 필요한 경우 별도로28을 조회합니다. 201을 받은 뒤 상세 조회가 실패해도 이미 접수된 사실은 유지하고 상세 확인 재시도로 안내합니다.
- 구매자는 REQUESTED·ACCEPTED 상태만 취소할 수 있습니다. 취소 요청에는 본문·취소 사유가 없습니다. 수락된 롤 취소는 확보 길이를 반환하고 자투리 취소는 예약 중 상태를 해제합니다. 이미 종료된 예약에는409 `INVALID_STATUS`가 옵니다.
- 목록은 상태 하나로 필터링하며 page는0부터, size는 기본20·최대50입니다. 최신 생성시각, 같은 시각이면 예약번호 내림차순입니다. 범위를 벗어난 페이지·실제 빈 내역·조회 오류를 구분하며 한 페이지의 건수를 전체 건수로 표시하지 않습니다.

## 시간은 한국 픽업 시간으로 처리

화면에서 고른 날짜·시간은 매장 방문 시간인 KST로 취급합니다. 전송할 때 `YYYY-MM-DDTHH:mm:00+09:00`처럼 시간대를 명시하고 유효한 날짜·시각 및 현재 이후인지 확인합니다. 서버는 ISO 8601의 오프셋 또는 `Z`를 받으며 시간대 없는 문자열과 과거 시각은400입니다.

응답은 `+09:00`을 포함한 한국 시간입니다. 조회·접수·취소 화면이 사용자의 브라우저 시간대에 따라 다른 방문 시각을 표시하지 않도록 KST 기준으로 변환합니다. 휴무·영업시간의 실제 예약 가능 여부는 이 API가 검증하지 않으므로 조회된 매장 안내와 판매자 수락 전에는 일정이 확정되지 않았다는 안내를 유지합니다.

| 데이터 | 목록26 | 상세28 | 표시 원칙 |
| --- | --- | --- | --- |
| 원단 | 최상위 `fabricId`, `title`, `thumbnail_url` | nested `fabric`의 번호·제목·판매 형태·상태·대표 사진 | 없는 사진은 사진 없음으로 표시 |

| 금액 | `estimated_price` | 동일 | 롤 요청 당시 예상금액. 자투리 null을0원으로 표시하지 않음 |
| 방문 장소 | 매장명, ACCEPTED에만 주소·픽업 안내 추가 | 모든 상태에서 매장명·주소·전화·휴무·픽업 안내 | 현재 매장 정보이며 예약 당시 스냅샷 아님 |

자투리는 `estimated_price=null`이며 예약 시점 금액을 조회할 수 없습니다. 롤은 요청 당시 가격으로 계산한 금액을 보존하지만 원단명·매장 주소·사진·도안명은 현재 연결 데이터를 읽습니다. 현재 매장 전화번호는 구매자의 연락처가 아닙니다. 예약별 이름·전화번호 입력·전달 계약도 없습니다.

판매 완료·소프트 삭제된 원단의 종료된 예약은 계속 조회할 수 있습니다. 예약 조회는 원단을 `paranoid: false`로 읽으므로 일반 구매자 원단 상세가404여도 예약 이력을 숨기지 않습니다. 예약의 원단 요약에는 삭제 여부가 없고 소프트 삭제 뒤에도 `status=POSTED`일 수 있습니다. 원단 상세·재예약 링크를 열었을 때의404를 별도로 처리하며 상태만 보고 현재 구매 가능하다고 확정하지 않습니다.

자투리 금액·치수·주소 등의 예약 시점 보존, 삭제 여부 표시에 필요한 계약 협의는 [API 후속 사항 B1](../../API_FOLLOWUPS.md#b1-예약-이력에-표시할-원단-정보와-금액)에 정리합니다. 현재 API로 가능한 내역·상세 표시와 추가 서버 계약이 필요한 정보는 구분합니다.

## 오류·응답 불명·409 복구 기준

| 상황 | 처리 기준 |
| --- | --- |
| 400 `VALIDATION_ERROR`, `LENGTH_NOT_MULTIPLE_OF_90` | 입력 오류를 안내하고 작성 내용을 유지 |
| 401 `UNAUTHORIZED` | 기존 세션 만료 처리. 서버 오류 코드를 `TOKEN_EXPIRED`로 가정하지 않음 |
| 403 `FORBIDDEN` / 404 `NOT_FOUND` | 접근 불가·예약 없음·원단 없음의 실제 응답을 표시하고 내역·목록으로 복귀 |
| 409 `DUPLICATE_RESERVATION` | 기존 요청을 확인하도록 안내. 오류 응답에는 기존 예약번호가 없음 |
| 409 `INSUFFICIENT_LENGTH`, `SCRAP_ALREADY_RESERVED`, `FABRIC_NOT_AVAILABLE` | 현재 원단·재고를 다시 확인하는 경로를 제공하고 성공으로 표시하지 않음 |
| 취소409 `INVALID_STATUS` | 현재 예약 상세를 다시 확인. 다른 처리로 종료됐을 수 있으므로 무조건 재취소하지 않음 |
| 생성·취소의 timeout·연결 종료·해석 불가능한 응답 | 서버 반영 여부가 불명일 수 있음. 실패 확정·자동 재전송 대신 내역·상세 확인 경로 제공 |

전송 중 중복 클릭을 막고 화면 이탈·로그아웃 뒤 늦은 응답이 다른 화면·세션을 변경하지 않도록 처리합니다. 클라이언트 요청을 취소해도 서버의 생성·취소가 되돌아갔다는 뜻은 아닙니다.

생성에는 멱등성 키가 없고 서버는 같은 구매자의 동일 원단 REQUESTED·ACCEPTED 중복을 막습니다. 응답 유실 뒤 기존 예약을 찾을 때 구매자 목록에는 `fabric_id` 필터가 없다는 점과 페이지 범위를 고려해야 합니다. 취소도 멱등 성공 응답이 아니어서 이미 CANCELED인 예약을 다시 취소하면409입니다. 재조회로 상태를 확인하지 않고 응답 유실을 미처리로 단정하지 않습니다.

## 서버 문서와 구현의 차이

- 명세29의 “같은 원단에 동시에 수락해도 한 건만 성공”은 자투리에만 정확합니다. 롤은 재고 안에서 여러 예약을 수락할 수 있고 서버 테스트에도 동시2건 성공이 있습니다. 구매자 화면은 이 문구로 롤 전체를 예약 중으로 잠그지 않습니다.
- 취소31·수령32의 오류표에는400이 빠져 있지만 잘못된 예약번호는 validator에서400을 반환합니다.
- OpenAPI는 예시에서 추출되어 ACCEPTED 목록의 추가 주소·픽업 안내가 스키마에 없고 여러 nullable 필드의 타입도 불완전합니다. 이번 변환은 명세 처리 규칙과 실제 서비스 DTO를 함께 기준으로 삼습니다.

근거: [API 명세][api] · [예약 서비스][service] · [validator][validator] · [조회 DAO][dao] · [서버 테스트][tests]. 백엔드 소스·명세는 이번 프론트 작업에서 수정하지 않습니다.

소프트 삭제된 원단의 이력은 백엔드 DAO·테스트 소스 및 프론트 DTO 독립성 검토로 확인했습니다. 이번 실서버 검증에서는 원단을 삭제하거나 매장 주소를 변경하지 않았습니다. 배포 환경과 판매자 예약 처리 UI도 이번 검증 범위 밖입니다.

독립 코드 검토에서 찾은 목록 복귀 시 page/size 유실과 브라우저 시간대에 따른 날짜 제한 불일치를 수정했고, 모델 테스트와 목록 복귀 브라우저 검증으로 확인했습니다.

검증 데이터는 `[예약 연동 검증 20261012]`로 표시한 가상 상품·매장입니다. 기존 사용자6·매장1·원단25·상세25·사진1·예약2는 내용 해시가 동일함을 확인했고, 새 QA 데이터만 사용했습니다. 테스트 계정·비밀번호·토큰·DB 환경설정·로컬 전용 시드 스크립트는 프론트 저장소에 포함하지 않습니다. 공개 요약에는 응답 본문과 인증 정보를 제외했습니다. 백엔드 소스 변경은 없고 검증 후 서버를 재시작했습니다.

`npm test`는 별도 서버 없이 재현할 수 있습니다. 실제 HTTP·브라우저 검증은 백엔드 README에 따라 로컬 DB·API와 테스트 데이터를 준비해야 하며, 이 저장소의 자동 명령에 포함하지 않았습니다. 기존 개발 DB를 초기화하는 백엔드 전체 테스트는 이번에 실행하지 않았습니다.
