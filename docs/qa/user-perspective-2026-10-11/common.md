# 공통 · 이용자 관점 검토

[전체 보고서](README.md) · [필터로 보기](index.html)

검토 2026-10-11~12. 우선순위와 검증 범위는 전체 보고서를 따른다. 이미지는 당시 실행 화면이며, 업무 상태 변경은 격리된 시연에서 확인했다.

## C01 · P2 · 일반 본문과 중요한 보조 정보가 작다

- 경로: 로그인·회원가입, 구매자 픽업, 판매자·관리자 상태 안내.
- 관찰: 기본 본문은 14px, 필드 라벨·도움말은 12px/줄높이 20px이다. 구매 조건·방문 시간·처리 효과처럼 놓치면 안 되는 정보도 작은 보조 문장으로 표현된다. 로그인 입력은 14px이며 버튼 높이는 48px이다.
- 영향: 화면은 정돈되어 보이지만 휴대폰에서 읽는 노력이 커진다. 내용의 중요도보다 컴포넌트 종류에 따라 글자 크기가 결정되어 핵심 조건이 덜 드러난다.
- 개선: 일반 본문·입력 16px, 핵심 메타 정보 14px 이상을 출발점으로 조정하고 짧은 부연에만 12px를 사용한다. 제목까지 일괄 확대하지 말고 정보의 중요도를 먼저 구분한다. 이는 디자인 권장값이며 WCAG가 본문 16px를 의무화한다는 의미는 아니다.
- 함께 수정: B08, A12는 같은 글자 문제의 업무별 사례다. 별도 공통 CSS 수정과 각 화면의 정보 재배치를 함께 확인한다.
- 증거: [mobile-login.jpg](screens/mobile-login.jpg), [mobile-pickup-top.jpg](screens/mobile-pickup-top.jpg); 실제 DOM 계산 스타일 확인.

## C02 · P2 · 일부 안내 글자와 입력 예시의 색 대비가 약하다

- 경로: 회원가입 비밀번호 입력 예시, 공통 화면 설명.
- 관찰: 실제 DOM의 비밀번호 placeholder는 #8e9a92/흰 배경으로 대비 약 2.92:1이다. 14px 공통 설명의 #68766f/#f7f8f4 조합은 약 4.47:1이다. CSS의 승인 대기 배지 조합 #9e6a19/#fff4d9는 약 4.24:1, 회색 배지 #67736a/#edf0ed는 약 4.32:1이다. 배지 수치는 CSS 토큰 계산이며 모든 배지 상태를 각각 DOM 측정한 것은 아니다.
- 영향: 밝은 화면이나 작은 글자에서 입력 조건·상태를 읽기 어렵다. 특히 비밀번호 길이가 예시 글자에만 있으면 낮은 대비와 입력 후 사라지는 문제가 겹친다.
- 개선: 전체의 녹색·아이보리 색감은 유지하고, 안내·placeholder·배지 글자 토큰을 각각 조정한다. 일반 크기 텍스트는 배경과 4.5:1 이상이 되도록 확인한다. 상태는 색 외에도 지금처럼 글자로 구분한다.
- 기준: W3C Contrast (Minimum), https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html . 대비는 sRGB 상대 휘도 공식으로 계산했다. 비활성 버튼은 이 판정 대상에서 제외했고, 사이트 전체 접근성 인증 결과는 아니다.
- 증거: [mobile-320-signup.jpg](screens/mobile-320-signup.jpg), [desktop-login.jpg](screens/desktop-login.jpg); 실제 DOM 색상과 CSS 토큰.

## C03 · P2 · 흰 카드 안의 입력란 경계가 흐리다

- 경로: 로그인·회원가입·등록 양식.
- 관찰: 활성 입력란의 테두리 #cdd8d0와 흰 배경의 대비는 약 1.47:1이다. 흰 카드와 흰 입력란 사이에서 테두리가 입력 영역을 구별하는 주된 단서다. 포커스 상태의 녹색 외곽선은 별도로 제공된다.
- 영향: 입력 전에는 어디부터 어디까지 눌러 입력할 수 있는지 구분이 약하다. 라벨이 보이더라도 입력 영역의 시각적 경계는 희미하다.
- 개선: 활성 컨트롤을 식별하는 경계는 충분히 선명하게 하고 포커스·오류 상태를 유지한다. 장식용 카드 구분선까지 모두 진하게 바꿀 필요는 없다. 필수 식별 경계는 인접 색과 3:1 기준으로 점검한다.
- 기준: W3C Non-text Contrast, https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html . 모든 장식 선에 3:1을 요구하는 것은 아니다.
- 증거: [desktop-login.jpg](screens/desktop-login.jpg), [mobile-320-signup.jpg](screens/mobile-320-signup.jpg); 실제 활성 입력의 계산 스타일 확인.

화면 증거: [1번 화면](screens/desktop-login.jpg) · [2번 화면](screens/mobile-320-signup.jpg)

## C04 · P2 · 비밀번호를 확인할 수 없고 길이 조건도 입력하면 사라진다

- 경로: `/auth/buyer/login`, `/auth/buyer/signup`; 판매자 공통 인증 양식.
- 관찰: 비밀번호와 확인 필드는 숨김 입력이며 표시/숨기기 버튼이 없다. 회원가입의 8~72자 안내는 placeholder에 있다.
- 영향: 특히 휴대폰에서 오타를 확인하기 어렵고, 작성 중 비밀번호 조건을 다시 읽기 어렵다.
- 개선: 접근 가능한 이름이 있는 ‘비밀번호 표시/숨기기’를 제공하고 길이 조건은 필드 아래에 계속 남긴다. 비밀번호 재설정 기능 확대와는 별개다.
- 증거: [mobile-signup-top.jpg](screens/mobile-signup-top.jpg), [desktop-login.jpg](screens/desktop-login.jpg); 실제 화면과 입력 DOM.

## C05 · P2 · 가입 동의 전에 약관과 개인정보 처리 내용을 열어볼 수 없다

**먼저 개선할 다섯 항목 중 하나.**

- 경로: `/auth/buyer/signup`, `/auth/seller/signup`의 공통 가입 양식.
- 관찰: 필수 동의 체크박스는 있지만 약관 내용을 여는 링크·버튼이 없다. 하단 ‘개인정보처리방침 · 이용약관’도 링크가 아닌 일반 문장이다. 실제 계정 모드의 빈 양식에서도 확인했으며 동의 체크나 가입 제출은 하지 않았다.
- 영향: 이용자는 무엇에 동의하는지 확인할 수 없는 상태에서 가입 여부를 결정해야 한다.
- 개선: 팀에서 확정한 약관·처리방침 내용을 ‘내용 보기’로 열고, 닫거나 돌아와도 입력값이 유지되게 한다. 동의 영역에 짧은 제목·필수 여부·내용 보기를 함께 배치한다.
- 구분: 프론트 링크/표시 구현과 운영 측 문안 확정이 함께 필요하다. 이번 항목은 동의 UX의 문제이며 법적 적합성을 판정한 결과는 아니다.
- 증거: [mobile-signup-consent.jpg](screens/mobile-signup-consent.jpg); 실제 화면의 링크 목록·DOM 확인.

화면 증거: [1번 화면](screens/mobile-signup-consent.jpg)

## C06 · P3 · 가입 화면에서 로그인으로 돌아가는 명확한 동선이 없다

- 경로: `/auth/buyer/signup`, `/auth/seller/signup`.
- 관찰: 구매자·판매자 가입 전환과 가입 버튼은 있지만 ‘이미 계정이 있나요? 로그인’ 또는 명시적 로그인 복귀가 없다. 브라우저 뒤로 가기에 의존한다.
- 영향: 기존 계정이 있다는 사실을 가입 도중 떠올린 사람이 다시 시작하는 방법을 찾아야 한다.
- 개선: 하단에 로그인 복귀를 제공하고 선택한 역할을 유지한다. 화면 내 이동이 있는 양식에서는 입력 초안 처리도 일관되게 한다.
- 증거: [mobile-signup-consent.jpg](screens/mobile-signup-consent.jpg), [mobile-320-signup.jpg](screens/mobile-320-signup.jpg).

## C07 · P2 · 공개 서비스의 첫 진입과 개발용 화면 모음을 분리할 필요가 있다

- 경로: 해시가 없는 첫 접속 → `/preview`.
- 관찰: 기본 진입은 역할별 시연 시작·상태 예시가 있는 화면 모음이다. 실제 계정 모드에도 개발용 상태 안내가 보인다. 현재 개발 검토에는 유용하다.
- 영향: 일반 이용자가 이 주소로 들어오면 서비스 이용보다 역할·시연·화면 상태를 먼저 이해해야 한다.
- 개선: 공개할 때 소비자용 첫 화면을 정하고 개발용 모음·상태 도구는 별도 진입으로 구분한다. 검토 도구는 팀이 계속 쓸 수 있게 유지한다.
- 구분: 현재 시연의 결함이 아니라 배포 전 정리 항목이다. 사업 데이터 API의 미연동 자체를 새 UX 결함으로 세지 않는다.
- 증거: 실제 화면 모음 진입과 App.jsx의 기본 경로 확인.

## C08 · P3 · 글꼴 파일 크기는 모바일 첫 방문 성능 점검 대상이다

- 경로: `public/assets/fonts/NotoSansKR-VF.ttf`, 공통 글꼴 선언.
- 관찰: 글꼴 파일은 10,415,532바이트(약 9.93MiB)이며 TTF 가변 글꼴을 사용한다. font-display: swap은 설정되어 있다.
- 영향: 캐시가 없는 모바일 접속에서는 글꼴 전송 비용이 클 가능성이 있다. 이번 검토에서 통신 제한을 걸어 지연 시간을 측정하지 않았으므로 ‘실제로 느렸다’고 단정하지 않는다.
- 개선: 차가운 캐시의 네트워크 측정 후 WOFF2·적절한 한글 서브셋·필요 굵기 범위를 검토한다. 브랜드 글꼴을 무조건 교체할 필요는 없다.
- 구분: 파일·소스에 근거한 성능 검증 후보. 직접 재현한 화면 결함과 구분한다.
