# 판매자 예약 조회·처리 API 연동

2026-10-12 KST · 백엔드 기준 `7dc28c79994295daee635524d05048574247a6d9`

실제 판매자 계정의 받은 예약 목록·상세·수락·거절·취소·수령 완료를 기존 API에 연결했습니다. **자동 테스트171개·lint·빌드와 로컬 HTTP109개 확인을 통과**했고, 구매자 화면의 새 요청부터 판매자 수락·수령 및 구매자 내역 반영까지 확인했습니다. 세부 검증 범위는 아래에 구분해 기록했습니다.

이번 `fetch origin main` 결과 HEAD와 origin/main이 모두 `7dc28c7`이며 추가 백엔드 커밋은 없었습니다. [구매자 예약 QA](../reservation-api-2026-10-12/README.md), [원단 조회 QA](../fabric-api-2026-10-12/README.md), [인증 QA](../auth-api-2026-10-11/README.md)는 당시 범위·결과를 보존합니다. 이전 문서의 판매자 예약 미연동 안내는 그 검증 시점의 상태입니다.

## 이번 연결 범위

기본 주소는 `/api/v1`이고 성공 응답은 `{ success: true, data }`입니다.

| API | 동작 | 요청 | 성공 응답 |
| --- | --- | --- | --- |
| 27 `GET /sellers/me/reservations` | 받은 예약 목록 | 선택 `status`, `fabric_id`, `page`, `size` | 페이지 DTO |
| 28 `GET /reservations/{reservationId}` | 예약 상세·처리 전후 확인 | 예약번호 | 상세 DTO |
| 29 `POST /reservations/{reservationId}/accept` | 요청 수락 | 본문 없음 또는 `{}`; 일시 변경 시 `pickup_at` | 200 `{ reservationId, status: "ACCEPTED" }` |
| 30 `POST /reservations/{reservationId}/reject` | 요청 거절 | `{ reason }`, trim 후1~255자 | 200 `{ reservationId, status: "REJECTED" }` |
| 31 `POST /reservations/{reservationId}/cancel` | 수락한 예약 취소 | 본문 없음 | 200 `{ reservationId, status: "CANCELED" }` |
| 32 `POST /reservations/{reservationId}/pickup` | 수령 완료 확인 | 본문 없음 | 200 `{ reservationId, status: "PICKED_UP" }` |

목록과 수락·거절·수령은 SELLER 전용이며, 상세·취소는 해당 예약의 판매자 또는 구매자에게 허용됩니다. 판매자 취소는 ACCEPTED만 가능하고 구매자의 취소 가능 상태와 다릅니다. 다른 판매자·구매자와 ADMIN은 당사자의 상세·처리 권한이 없습니다. 판매자 승인 상태를 별도로 요구하는 미들웨어는 이 예약 경로에 없습니다. 원단 등록 권한의 승인 조건을 예약 조회 권한과 혼동하지 않습니다.

실제 예약 화면은 서버에서 읽은 상태와 성공 응답을 기준으로 갱신합니다. 시연 모드와 실제 계정의 예약 데이터·동작은 분리합니다. 대시보드의 요청 중·수락한 예약 전체 건수도 각 상태의 서버 목록 조회로 연결합니다. 원단 등록·편집·사진 업로드, 문의 답변, 관리자 처리, 원단·문의 통계와 달력 날짜별 집계는 이번 범위 밖입니다. 이 중 서버에 이미 구현된 기능을 새 API 요청으로 다루지 않습니다.

## 목록과 상세 계약

목록27의 각 항목은 `reservationId`, `status`, `pickup_at`, `memo`, `requested_length_cm`, `estimated_price`, `fabricId`, `title`, `buyer_nickname`입니다. 구매자 목록26과 필드가 다르므로 구매자 DTO 검증을 그대로 적용하지 않습니다.

| 항목 | 판매자 목록27 | 상세28 | 표시 기준 |
| --- | --- | --- | --- |
| 판매 형태·수량 | 판매 형태 필드 없음, 요청 길이 있음 | `fabric.sale_type`, 요청 길이 | null 길이는 자투리, 90배수 길이는 롤 계약으로 구분 |
| 금액 | `estimated_price` | 동일 | 롤은 요청 당시 예상금액. 자투리 null을0원·현재 단가로 보충하지 않음 |
| 원단 제목·사진 | 제목 있음, 사진 필드 없음 | `fabric.title`, nullable `fabric.thumbnail_url` | 목록에 없는 사진을 예시 상품 사진으로 채우지 않음 |
| 구매자 | `buyer_nickname` | 동일 | 전화번호·이메일은 제공되지 않음 |
| 메모·거절 사유 | nullable `memo`, 거절 사유 없음 | `memo`, nullable `reject_reason` | 목록에 없는 사유는 상세에서 확인 |
| 예약 처리 이력 | 없음 | `accepted_at`, `picked_up_at`, `canceled_at`, `canceled_by`, `created_at` | 미처리 시각·취소 주체는 null일 수 있음 |
| 원단·매장 | 원단 번호·제목 | `fabric` 요약, `store` 매장 정보, nullable `pattern_name` | 현재 정보이며 예약 시점 스냅샷 아님 |

상세의 `fabric`은 번호·제목·판매 형태·상태·대표 사진만 포함합니다. 원단 치수·단가·재고·삭제 여부는 없습니다. `store`는 매장명·주소·전화·휴무·픽업 안내이며 `store_phone`을 구매자 연락처로 표시하지 않습니다. 사진은 서버의 HTTP(S) URL을 사용하며 null·로드 실패는 해당 상태로 표시합니다.

목록 응답은 `content`, `page`, `size`, `totalElements`, `totalPages`입니다. page는0부터, size는 기본20·최대50이며 정렬은 생성일 내림차순, 같은 시각이면 예약번호 내림차순입니다. 픽업 일정순이 아닙니다. `status`는 상태 하나이며 생략하면 전체 상태, `fabric_id`는 한 원단 필터입니다. 다른 판매자의 원단번호로 목록을 필터링하면 빈 결과이고, 다른 사람의 특정 예약 상세를 열면403입니다.

목록은 픽업 날짜 범위·검색어·달력 전용 조회를 지원하지 않습니다. 상태별 별도 집계 API는 없지만 `status=REQUESTED`와 `status=ACCEPTED`를 각각 조회한 `totalElements`로 해당 상태의 전체 건수를 얻을 수 있습니다. 대시보드는 이 서버 건수를 사용하며 내려받은 한 페이지의 행 수로 대체하지 않습니다. 달력 날짜별 집계는 연결하지 않고 일부 페이지를 전체 방문 일정으로 표시하지 않습니다. 목록 상태·원단 필터·페이지에서 상세·처리 화면으로 갔다가 돌아올 때 원래 조회 조건을 보존하는 것을 검증합니다.

## 시간과 상태 전환

응답 시각은 KST `+09:00` ISO 형식입니다. 브라우저 시간대와 관계없이 한국 매장 시간을 표시합니다. 이번 판매자 UI는 기존 희망 일시를 유지해 수락하는 흐름입니다. 일시 변경 입력은 서버와 서비스 어댑터가 지원하는 계약이며, 변경용 화면까지 연결했다고 의미하지 않습니다.

수락할 때 일시를 변경하지 않는 경우 `pickup_at`을 보내지 않습니다. 변경할 때만 ISO 오프셋을 명시한 현재 이후의 시각을 보냅니다. 서버는 `+09:00`과 `Z`를 모두 받지만 시간대 없는 문자열·과거 변경시각은400입니다. 원래 희망 일시가 지났더라도 본문 없는 수락 자체는 서버가 허용합니다. 이를 “기존 일시를 다시 전송”하는 구현으로 바꾸면 원치 않는400이 발생할 수 있습니다.

| 처리 | 허용 상태·조건 | 재고·관련 예약 변화 |
| --- | --- | --- |
| 수락29 | REQUESTED, 원단 POSTED, 현재 재고 확보 가능 | 자투리는 예약 중, 롤은 요청 길이만큼 확보 길이 증가 |
| 거절30 | REQUESTED, 사유 필수 | 재고 변화 없음, `reject_reason` 기록 |
| 판매자 취소31 | ACCEPTED만, 본문·취소 사유 없음 | 확보 재고 반환, `canceled_by=SELLER`·취소시각 기록 |
| 수령32 | ACCEPTED | 자투리는 SOLD_OUT. 롤은 남은 길이와 확보 길이를 요청 길이만큼 차감 |

롤은 수령 후 남은 길이가90cm 미만일 때 SOLD_OUT이며 정확히90cm이면 게시 상태를 유지합니다. SOLD_OUT이 되면 같은 원단의 다른 REQUESTED 예약은 `판매 완료` 사유로 자동 REJECTED됩니다. 수락 직후에는 나머지 요청을 자동 거절하지 않습니다. 처리 뒤 선택한 행만 임의로 바꾸지 않고 서버 목록·상세를 다시 확인해야 합니다.

서버는 수령 확인 시 방문 예정시각이 지났는지 검사하지 않습니다. 수령 처리는 실제 인도가 끝났을 때 판매자가 확인하는 동작이며 시간 경과만으로 자동 실행하지 않습니다. 휴무·운영시간 역시 자동 검증 계약이 아닙니다.

## 오류와 응답 유실

- 400 `VALIDATION_ERROR`: 예약번호·거절 사유·변경 일시를 확인합니다. 상세 항목 오류와 입력 초안을 유지합니다.
- 401 `UNAUTHORIZED`: 기존 세션 만료 흐름으로 처리합니다. 서버 코드가 `TOKEN_EXPIRED`인 것으로 가정하지 않습니다.
- 403 `FORBIDDEN`, 404 `NOT_FOUND`: 권한 없는 예약과 존재하지 않는 예약을 구분합니다. 당사자 확인은 상태 확인보다 먼저 수행됩니다.
- 409 `INVALID_STATUS`: 다른 처리로 상태가 바뀌었을 수 있습니다. 수락 시 원단이 POSTED가 아닌 경우도 이 코드입니다. 현재 상태를 다시 조회한 뒤 가능한 동작을 결정합니다.
- 수락의409 `SCRAP_ALREADY_RESERVED`, `INSUFFICIENT_LENGTH`: 요청 이후 다른 예약이 먼저 재고를 확보했을 수 있습니다. 수락 성공으로 표시하지 않고 현재 정보를 다시 확인합니다.
- timeout·연결 종료·해석할 수 없는 성공 응답은 처리 여부가 불명일 수 있습니다. 상태 전환 POST를 자동 재전송하지 않고 상세·목록 확인 경로를 제공합니다. 이미 처리된 요청을 반복하면 멱등 성공이 아니라409가 될 수 있습니다.

200 상태 전환 응답을 받은 뒤 상세 재조회가 실패하면 처리 완료와 조회 실패를 분리합니다. 재조회 실패 때문에 동일한 상태 전환을 다시 보내지 않습니다. 연속 클릭과 화면 이탈·로그아웃 뒤 지연 응답이 중복 처리 또는 다른 화면의 성공 안내를 만들지 않도록 검증합니다. 클라이언트 요청 중단은 서버 처리가 되돌아갔다는 증거가 아닙니다.

## 이력 보존과 남은 서버 협의

예약 DAO는 원단을 `paranoid: false`로 읽으므로 판매 완료·소프트 삭제 원단의 종료된 예약도 조회할 수 있습니다. 일반 원단 조회 실패를 예약 이력 표시의 전제조건으로 삼지 않습니다. 삭제 여부 필드가 없어 `fabric.status=POSTED`만으로 현재 원단 상세를 열 수 있다고 확정할 수도 없습니다.

롤 예상금액 외에 원단명·사진·매장 주소·도안명은 현재 연결 데이터를 읽습니다. 자투리 금액·원단 치수·당시 방문 정보의 보존은 [API 후속 사항](../../API_FOLLOWUPS.md)의 협의 범위이며 이번 화면에서 임의 값을 채워 해결하지 않습니다. 구매자 전화번호 제공과 별도 예약 연락처 저장도 현재 계약에 없습니다.

서버 명세29의 “같은 원단에 동시에 수락해도 한 건만 성공”은 자투리에만 맞습니다. 롤은 재고 안에서 여러 건이 성공하며 서버 테스트에도 동시2건 성공 사례가 있습니다. 수령32의 개별 오류표에는 잘못된 ID에 대한400이 빠져 있고, OpenAPI는 예시 기반이라 여러 nullable 필드의 타입이 불완전합니다. 실제 서비스·validator·테스트와 함께 계약을 해석합니다.

| 새로고침·모바일 | 완료 상세 새로고침 후 인증·필터·선택 복구. 390×844 viewport의 상세·취소 확인 검토, 상세 clientWidth=scrollWidth=375로 가로 넘침 없음 |
| 브라우저 오류 | 최종 새로고침 이후 수집된 console error/warn 없음 |

응답 유실·timeout·500·잘못된 성공 응답·이전 계정의 늦은200/401/500, 화면 이탈·중복 클릭은 모의 HTTP와 lifecycle 자동 테스트로 확인했습니다. 이번 브라우저 검증에서 서버 중단이나 POST 반영 후 응답 유실을 강제로 재현하지는 않았습니다. 200 응답 뒤 상세 GET 실패의 처리 완료 안내는 구현·독립 코드 검토 범위입니다. 예약 조회 실패·시연 격리·구매자 회귀는 기존 자동 테스트도 함께 통과했습니다.

소프트 삭제 원단의 예약 이력은 DAO와 프론트 DTO 독립성의 코드 검토 범위이며 이번 검증에서 원단을 삭제하지 않았습니다. 판매 완료 예약은 실제 HTTP로 조회했습니다. 별도 일정 변경 UI, 원단·문의 집계, 날짜별 달력 집계와 배포 서버는 이번 범위 밖입니다.

검증용 사용자·매장·원단은 `[판매자 예약 검증 20261012]` 가상 데이터이며 실제 거래가 아닙니다. 기존 사용자9·매장2·원단33·상세33·사진1·예약32를 포함한 11개 모델의 기존 행 해시가 HTTP 및 브라우저 처리 후에도 동일했습니다. 백엔드 소스 변경·개발 DB 초기화 없이 새 검증 데이터만 처리했고 두 로컬 서버는 정상 실행 중입니다.

`npm test`는 서버 없이 재현할 수 있습니다. 실제 HTTP·브라우저 확인은 별도 로컬 DB·API·가상 데이터를 준비해야 합니다. 개발 DB를 초기화하는 백엔드 전체 테스트는 실행하지 않았습니다.
