## B1. 예약 이력에 표시할 원단 정보와 금액

**기존 계약으로 구매자 예약 흐름과 판매자 예약 처리를 연결했습니다. 남은 협의는 예약 시점 정보와 자투리 금액·치수의 보존입니다.** 구매자 요청25·내 목록26·상세28·취소31과 판매자 목록27·상세28·수락29·거절30·취소31·수령32의 검증 결과는 각각의 QA 기록에서 확인합니다.

- 구매자 예약 목록(26)은 원단명·대표 사진·매장명을 반환하고, `ACCEPTED`에는 `store_address`, `pickup_guide`도 반환합니다. 예약 상세(28)는 원단 요약과 매장 주소·전화·휴무·픽업 안내를 제공합니다. 방문 정보 표시를 위해 별도의 신규 API가 반드시 필요한 것은 아닙니다.
- 판매자 받은 목록(27)은 구매자 닉네임·메모·요청 수량·예상금액·원단명·픽업 일시를 반환합니다. 목록에는 사진·판매 형태·거절 사유·처리 시각이 없으므로 상세28에서 제공하는 정보와 구분합니다. 기존 상세 계약으로 볼 수 있는 정보를 새 API 요구사항으로 중복 요청하지 않습니다.
- 예약 DAO는 원단을 `paranoid: false`로 조회하므로 판매 완료·소프트 삭제된 원단의 종료된 예약도 조회할 수 있습니다. 일반 구매자 원단 상세가 404라는 이유로 예약 이력까지 조회 불가라고 판단하지 않습니다.
- 예약 응답에는 원단의 삭제 여부가 없습니다. 소프트 삭제 후에도 원단 `status`가 POSTED일 수 있으므로 이를 현재 상세·재예약 가능 여부의 확정 근거로 쓰지 않습니다. 예약 이력을 먼저 보여 주고 현재 원단을 여는 동작의 404를 별도로 처리할 수 있습니다. 직접적인 판매 종료 표시가 필요하면 삭제 여부 필드의 추가를 협의합니다.
- 다만 원단명·매장·사진은 현재 연결된 데이터를 읽습니다. 예약 당시 제목·주소·사진이 고정되는 스냅샷은 아닙니다. 예약 후 변경된 값을 표시할지, 당시 값을 보존할지 합의해야 합니다.
- 롤의 `estimated_price`는 요청 당시 가격으로 고정됩니다. **자투리의 `estimated_price`는 여전히 null**이며 예약 응답의 원단 요약에 치수·가격은 없습니다. 자투리 금액과 양쪽 판매 형태의 치수 이력을 표시하려면 응답 필드·저장 정책을 추가로 정해야 합니다.
- 자투리의 null 금액을 0원이나 현재 원단 가격으로 채우지 않고 금액 정보가 제공되지 않았음을 표시합니다. 예약의 치수도 시연 값으로 보충하지 않습니다. `display_price`, `fabric_title` 같은 프론트 표시 모델은 실제 `estimated_price`, `title` 등을 변환한 값이며 별도 서버 필드가 아닙니다.
- 생성·취소·수락·거절·수령의 응답 유실은 서버 처리 실패의 증거가 아닙니다. 기존 내역·상세 조회로 확인하는 복구는 프론트에서 다루며, 서버 멱등성 키·생성 결과 조회용 키는 현재 계약에 없습니다. 이미 처리된 상태 전환을 다시 요청하면 409이고, 중복 예약 오류에는 기존 예약번호가 포함되지 않습니다. 향후 자동 복구 수준을 높일 필요가 있을 때 추가 계약을 협의합니다.

## B2. 원단 생성과 사진 업로드의 실패 복구

**생성·사진 업로드·삭제 API는 존재합니다. 남은 협의는 불확실한 응답과 중단된 등록의 복구 정책입니다.** 원단 생성 후 받은 `fabricId`로 사진을 별도 업로드하는 계약이며, 생성 즉시 상태는 PENDING입니다. 일부 사진 실패 시 같은 원단에서 실패한 사진만 재시도하고 생성 요청을 다시 보내지 않는 방향을 유지합니다.

직접 원단 목록14·상세11·등록9·수정12·삭제13·사진15~16의 프론트 연결과 로컬 검증을 완료했습니다. 원단·사진 단위의 재조회와 오류 복구 구현으로 다룬 부분과 아래의 서버 정책 협의를 구분합니다. AI17~21 연결은 이 작업의 완료 범위에 포함하지 않습니다.

- 직접 생성 요청은 처리됐지만 응답을 받지 못한 경우, 또는 사진 업로드는 성공했지만 응답이 유실된 경우의 재조회·중복 방지 정책을 합의합니다. 프론트 버튼 잠금만으로 서버 중복 생성을 막을 수는 없습니다.
- 내 원단 목록(14)·상세(11)로 원단과 올라간 사진을 조회하고, 사진 삭제(16)·원단 삭제(13)를 사용할 수 있습니다. 이 기능을 활용한 재개·정리 절차를 정하되 진행 중 예약이 있는 원단의 삭제 제한을 지킵니다.
- 사진이 없는 원단은 게시 승인할 수 없지만, 사진이 일부 올라간 PENDING 원단을 언제 검토 가능한 것으로 볼지는 별도 정책입니다. 사진 한 장의 존재가 사용자가 의도한 전체 업로드 완료를 의미하지는 않습니다.
- AI 확정(20)은 세션별 잠금과 상태 검사를 사용합니다. 이를 직접 등록의 멱등성 키나 서버 재시작·응답 유실에 대한 포괄적인 복구 보장과 동일하게 취급하지 않습니다.
- 서버 DRAFT·submit·멱등성 키는 현재 확정된 기능으로 약속하지 않습니다.

## B3. 예약 연락처의 의미와 노출 범위

**계약 협의가 남아 있습니다.** 예약 생성 계약에는 예약별 이름·전화번호 입력이 없습니다. 판매자 받은 예약 목록(27)은 `buyer_nickname`을 제공하지만 구매자 전화번호는 제공하지 않습니다. 예약 상세의 `store_phone`은 매장 연락처이며 구매자 연락처가 아닙니다.

- 화면이 계정 정보를 확인하는 것인지, 별도 예약 연락처를 저장하는 것인지 팀에서 결정해야 합니다.
- 별도 저장이 필요하면 필수 여부·계정 값과 다른 경우·판매자에게 노출할 시점을 합의합니다.
- 계약이 정해지기 전에는 화면 입력만으로 예약 연락처가 저장되거나 전달됐다고 안내하지 않습니다.

## B4. 부가 화면과 기능의 범위

- 매장 등록·수정: 기존5~7 계약의 프론트 연결과 로컬 검증을 완료했으며 신규 API 요청 대상이 아닙니다. 판매자 승인 여부와 무관하게 자기 매장을 저장할 수 있고, 저장으로 판매자 승인이 바뀌거나 재신청되는 것은 아닙니다. 주소는 `store_address` 한 필드이며 별도 `detail_address` 계약은 없습니다. 휴무일·픽업 안내는 null을 허용하지만 생성된 OpenAPI의 응답 스키마에는 nullable 표시가 빠져 있어 실제 validator·서비스·테스트와 구분합니다. 개인 프로필 수정4와 매장 저장을 한 번의 성공으로 처리하지 않습니다.

- 판매자 예약 처리: 받은 목록27·상세28·수락29·거절30·취소31·수령32를 이번 후속 프론트 작업으로 연결했습니다. 판매자는 ACCEPTED만 취소할 수 있고 REQUESTED에는 거절을 사용합니다. 모두 기존 계약이며 신규 API를 요청할 사안은 아닙니다.
- 판매자 대시보드 통계: 요청 중·수락한 예약은 목록27, 원단 상태별 건수는 내 원단 목록14, 답변 대기·완료는 받은 문의 목록44의 상태 필터와 `totalElements`로 연결했습니다. 전용 통계 API가 반드시 필요한 것은 아닙니다. 문의의 답변 완료 코드는 `ANSWERED`이고 시연 화면의 `DONE`과 다릅니다. 원단 통계는 삭제 원단을 제외하지만 문의 통계에는 삭제된 원단에 남은 문의가 포함될 수 있습니다.
- 판매자 픽업 달력: 목록27에는 픽업 날짜 범위·달력 전용 조회가 없지만, `ACCEPTED`의 모든 페이지를 읽고 KST 픽업 날짜로 묶어 연결했습니다. 일부 페이지만 읽은 결과를 전체 일정으로 표시하지 않으며 페이지 실패·중복·건수 변경을 확인합니다. 이 계약은 조회 시점이 고정된 스냅샷이 아니므로 조회 도중 상태가 바뀌면 모든 변경을 감지할 수는 없습니다. 월별 서버 필터·커서·조회 버전 또는 집계 API는 데이터 규모와 동시 변경에 따른 필요가 확인되면 협의할 개선 사항이며, 현재 화면 연결의 선행 필수 API로 요청하지 않습니다.
- 구매자 본인 문의 목록: 원단별 문의 작성·목록(42·43), 판매자 받은 문의·답변(44·45)은 서버에 구현됐습니다. 전체 원단에 걸친 구매자 본인 문의 목록은 별도이며 `GET /inquiries/me`는 여전히 제안 경로입니다. 문의 수정·삭제(46·47)는 명세에 있으나 현재 routes에서 구현을 확인하지 못했습니다.
- 추천·도안: 기존22~24의 프론트 연결과 실제 예약까지의 로컬 검증을 완료했습니다. 도안 부품·허용 소재/두께·판정 근거·롤 구매 길이/금액은 기존 계약으로 조회하므로 신규 API가 선행 필수인 항목이 아닙니다. 자투리 추천 금액은 null이고 화면의 한 장 전체 가격은 현재 원단 상세에서 확인한 값입니다. 추천 결과는 적합5개·소재 확인 필요3개 제한이 있어 누락된 도안을 제작 불가로 단정하지 않습니다. 시접 포함 여부·부자재·실제 크기 출력 파일은 현재 계약에 없으며 임의로 채우지 않습니다. 배포용 도안의 제작 검토·이미지 사용 권리는 별도로 확인해야 합니다.
- 추천과 예약의 경계: 예약25는 pattern_id의 존재·활성 여부를 검사하지만 원단과의 적합성·권장 수량을 다시 계산하지 않습니다. 프론트는 전송 직전 추천·도안·원단을 재조회하고 가격·판매 방식 변경, 소재 확인 필요, 권장 길이 미만을 차단합니다. 여러 GET과 POST가 한 트랜잭션은 아니므로 재조회 이후 변경까지 원자적으로 보장하지 않습니다. 이 보장이 필요해지면 추천 버전 또는 예약 시 조건 검증 계약을 협의합니다.
- AI 등록: 세션17~21 서버 라우트는 있지만 프론트의 AI 예시는 실제 API 연결 완료가 아닙니다. 요구사항 P0이므로 선택 기능으로 낮추지 않고 남은 핵심 연결 M5로 관리합니다. 서버 AI 제공자(fake/openai)와 메모리 세션의 실제 호출·재시작·이력 보존 검증 범위도 구분합니다.
- 등록 시간·게시 후 비공개: 요구사항 정의서 FAB-13·ADMIN-02는 P0입니다. 현재 일반 등록 입력에는 등록 방식·시작/완료 시각이 없으며 관리자 원단 승인/반려는 PENDING에서만 가능합니다. 별도 기록/계약 또는 요구사항 조정이 필요하므로 기존 프론트 연결만으로 충족했다고 보고하지 않습니다.
- 관심 저장(39~41): 서버 구현과 계약이 있습니다. 신규 API가 필요한 것으로 요청하지 않고 별도 프론트 연동 대상으로 관리합니다.
- 관리자 조회·승인: 기존33~38의 연결·검증을 완료했습니다. 원단 승인/반려는 PENDING만, 판매자 승인은 PENDING·REJECTED에서 가능하고 판매자 거절은 PENDING만 가능합니다. 원단 반려는 사유를 받지만 판매자 거절은 요청 본문·사유 저장 계약이 없습니다. 매장 미등록 판매자도 승인 API의 대상이며, 이후 원단 등록에는 별도로 매장이 필요합니다.
- 관리자 선택 상세: 전용 `GET /admin/sellers/{id}`·`GET /admin/fabrics/{id}`는 없습니다. 판매자 상세는 기존 상태별 목록의 페이지 탐색으로 구성할 수 있으나 조회량과 동시 상태 변경의 한계가 있습니다. 원단은 기존 일반 상세11을 ADMIN 권한으로 조회할 수 있으며 관리자 목록에 없는 반려 사유·가용/확보 길이·매장 주소를 제공합니다. 이미 조회 가능한 원단 정보를 신규 API의 선행 요구로 중복 요청하지 않습니다.
- 관리자 구매자 조회·추가 통계·상태 외 검색: 관리자 목록은 `status`, `page`, `size`만 받으며 생략 상태는 PENDING입니다. 기본 상태별 통계는 `totalElements`로 집계할 수 있습니다. 여러 응답을 합한 비원자적 집계와 내려받은 한 페이지의 행 수를 구분하고, 별도 구매자 조회·추가 필터·집계가 필요하면 계약을 확정합니다.
- 공장 목록과 부자재 지도: **`GET /factories`(48)가 추가됐습니다.** 업종 `category`·페이지 조건으로 양주시청 공장등록 자료를 조회하고 이름·주소·생산품·분류·좌표·출처를 반환합니다. 좌표는 null일 수 있습니다. 이 목록은 협력 매장이나 부자재 소매 판매처가 확인된 목록이 아니므로 기존 지도 예시와 바로 동일시하지 않습니다. 실제 화면에 사용할 대상·좌표 없는 항목의 표시 방식을 정하고 별도로 연동합니다.
- 이메일·비밀번호 변경: 전용 API·재인증·기존 토큰 처리 계약이 필요하며 현재 보류 화면을 임의로 복원하지 않습니다.

현재 화면 구현과 API 연결 범위는 [README](../README.md), 연결 순서는 [React 개발 기준](REACT_MIGRATION.md)에 정리되어 있습니다. 담당자·구현 일정과 최종 계약은 팀 합의 후 이 문서에 반영합니다.
