# 후속 API 협의 사항

2026-10-12에 백엔드 main `7dc28c79994295daee635524d05048574247a6d9`의 [API 명세 v0.3][api]과 서버 소스를 대조해 갱신했습니다. 2026-10-11 인증 통합 검증의 기준 `e177ea6`에서 7개 커밋이 추가됐으며, 원단 조회·예약·추천·AI 등록·문의·관심 저장·공장 목록 구현이 추가됐습니다. 서버 구현과 프론트 연동 완료는 별개입니다. 이번 프론트 작업은 [구매자 원단 목록·상세 조회](qa/fabric-api-2026-10-12/README.md)이며, 실제 쓰기 기능까지 연결했다고 의미하지 않습니다.

아래의 미확정 필드·정책·제안 URL은 팀 협의 대상입니다. 기존 계약에 있는 기능은 새 API로 요청하지 않고 구현·연동 상태를 구분합니다.

## B1. 예약 이력에 표시할 원단 정보와 금액

**일부 해소: 현재 원단·매장 정보를 포함한 예약 조회는 구현됐습니다. 예약 시점 정보의 보존은 별도 협의가 남았습니다.**

- 구매자 예약 목록(26)은 원단명·대표 사진·매장명을 반환하고, `ACCEPTED`에는 `store_address`, `pickup_guide`도 반환합니다. 예약 상세(28)는 원단 요약과 매장 주소·전화·휴무·픽업 안내를 제공합니다. 방문 정보 표시를 위해 별도의 신규 API가 반드시 필요한 것은 아닙니다.
- 예약 DAO는 원단을 `paranoid: false`로 조회하므로 판매 완료·소프트 삭제된 원단의 종료된 예약도 조회할 수 있습니다. 일반 구매자 원단 상세가 404라는 이유로 예약 이력까지 조회 불가라고 판단하지 않습니다.
- 다만 원단명·매장·사진은 현재 연결된 데이터를 읽습니다. 예약 당시 제목·주소·사진이 고정되는 스냅샷은 아닙니다. 예약 후 변경된 값을 표시할지, 당시 값을 보존할지 합의해야 합니다.
- 롤의 `estimated_price`는 요청 당시 가격으로 고정됩니다. **자투리의 `estimated_price`는 여전히 null**이며 예약 응답의 원단 요약에 치수·가격은 없습니다. 자투리 금액과 양쪽 판매 형태의 치수 이력을 표시하려면 응답 필드·저장 정책을 추가로 정해야 합니다.
- 시연용 `display_price`, `fabric_title` 등을 실제 응답 필드로 간주하지 않습니다. 예약 프론트 연동은 이번 원단 조회 작업의 범위 밖입니다.

## B2. 원단 생성과 사진 업로드의 실패 복구

**생성·사진 업로드·삭제 API는 존재합니다. 남은 협의는 불확실한 응답과 중단된 등록의 복구 정책입니다.** 원단 생성 후 받은 `fabricId`로 사진을 별도 업로드하는 계약이며, 생성 즉시 상태는 PENDING입니다. 일부 사진 실패 시 같은 원단에서 실패한 사진만 재시도하고 생성 요청을 다시 보내지 않는 방향을 유지합니다.

- 직접 생성 요청은 처리됐지만 응답을 받지 못한 경우, 또는 사진 업로드는 성공했지만 응답이 유실된 경우의 재조회·중복 방지 정책을 합의합니다. 프론트 버튼 잠금만으로 서버 중복 생성을 막을 수는 없습니다.
- 내 원단 목록(14)·상세(11)로 원단과 올라간 사진을 조회하고, 사진 삭제(16)·원단 삭제(13)를 사용할 수 있습니다. 이 기능을 활용한 재개·정리 절차를 정하되 진행 중 예약이 있는 원단의 삭제 제한을 지킵니다.
- 사진이 없는 원단은 게시 승인할 수 없지만, 사진이 일부 올라간 PENDING 원단을 언제 검토 가능한 것으로 볼지는 별도 정책입니다. 사진 한 장의 존재가 사용자가 의도한 전체 업로드 완료를 의미하지는 않습니다.
- AI 확정(20)은 세션별 잠금과 상태 검사를 사용합니다. 이를 직접 등록의 멱등성 키나 서버 재시작·응답 유실에 대한 포괄적인 복구 보장과 동일하게 취급하지 않습니다.
- 서버 DRAFT·submit·멱등성 키는 현재 확정된 기능으로 약속하지 않습니다.

## B3. 예약 연락처의 의미와 노출 범위

**계약 협의가 남아 있습니다.** 예약 생성 계약에는 예약별 이름·전화번호 입력이 없습니다. 판매자 받은 예약 목록(27)은 `buyer_nickname`을 제공하지만 구매자 전화번호는 제공하지 않습니다. 예약 상세의 `store_phone`은 매장 연락처이며 구매자 연락처가 아닙니다.

- 화면이 계정 정보를 확인하는 것인지, 별도 예약 연락처를 저장하는 것인지 팀에서 결정해야 합니다.
- 별도 저장이 필요하면 필수 여부·계정 값과 다른 경우·판매자에게 노출할 시점을 합의합니다.
- 계약이 정해지기 전에는 화면 입력만으로 예약 연락처가 저장되거나 전달됐다고 안내하지 않습니다.

## B4. 부가 화면과 기능의 범위

- 구매자 본인 문의 목록: 원단별 문의 작성·목록(42·43), 판매자 받은 문의·답변(44·45)은 서버에 구현됐습니다. 전체 원단에 걸친 구매자 본인 문의 목록은 별도이며 `GET /inquiries/me`는 여전히 제안 경로입니다. 문의 수정·삭제(46·47)는 명세에 있으나 현재 routes에서 구현을 확인하지 못했습니다.
- 관심 저장(39~41): 서버 구현과 계약이 있습니다. 신규 API가 필요한 것으로 요청하지 않고 별도 프론트 연동 대상으로 관리합니다.
- 관리자 구매자 조회·추가 통계·상태 외 검색: 현재 관리자 원단·판매자 목록은 `status`, `page`, `size`를 받습니다. 필요한 추가 데이터와 필터·집계 계약을 확정하며, 내려받은 한 페이지의 결과를 전체 검색·통계로 표시하지 않습니다.
- 공장 목록과 부자재 지도: **`GET /factories`(48)가 추가됐습니다.** 업종 `category`·페이지 조건으로 양주시청 공장등록 자료를 조회하고 이름·주소·생산품·분류·좌표·출처를 반환합니다. 좌표는 null일 수 있습니다. 이 목록은 협력 매장이나 부자재 소매 판매처가 확인된 목록이 아니므로 기존 지도 예시와 바로 동일시하지 않습니다. 실제 화면에 사용할 대상·좌표 없는 항목의 표시 방식을 정하고 별도로 연동합니다.
- 이메일·비밀번호 변경: 전용 API·재인증·기존 토큰 처리 계약이 필요하며 현재 보류 화면을 임의로 복원하지 않습니다.

현재 화면 구현과 API 연결 범위는 [README](../README.md), 연결 순서는 [React 개발 기준](REACT_MIGRATION.md)에 정리되어 있습니다. 담당자·구현 일정과 최종 계약은 팀 합의 후 이 문서에 반영합니다.
