# 패브링 프론트엔드

2026-10-11 최종 UX 검토를 마친 HTML을 **React 19 + Vite**로 전환했습니다. 현재 기본 진입점은 React입니다. 활성177개 화면/상태·해시 URL과 시연 데이터를 유지하며, 후속 [배치 재검토](docs/qa/layout-polish-2026-10-11/README.md)에서 관리자 하단 여백·반응형 목록·역할별 고정 높이 등을 수정했습니다.

## 패브링 디자인 적용 · 2026-10-13

승인한 코발트 `#2458C6`와 로고 02의 연결 원단 심볼, 한글 패브링 이름을 실제 React 구매자·판매자·관리자·로그인 화면에 적용했습니다. 사진 중심 목록, 가격·판매 단위·치수 우선 상세, 판매자 업무 목록, 관리자 승인 큐, 등록 단계와 입력/오류 규칙을 정리했습니다. 자투리/롤 탭에서도 검색 조건을 유지합니다.

역할별 화면을 필요할 때 불러오고 데님 이미지를 WebP로 최적화했습니다. 최초 앱 JavaScript는 약305KB(압축 약93KB)이며 500KB 초과 빌드 경고를 해소했습니다. 기존 API·권한·예약 재고·사진 복구 계약과 관심 저장/공모전 계정 안내를 유지합니다. [변경·전체 로컬 검증 기록](docs/qa/fabring-production-2026-10-13/README.md)에서 관리자 변경과 실제 거래·문의 흐름의 검증을 확인할 수 있습니다.

## 실행과 확인

검증 환경은 **Node.js 24.18.0 / npm 11.16.0**입니다. `.nvmrc`에 Node 버전을 기록했고, 의존성은 `package-lock.json` 기준으로 설치합니다. Windows에서는 아래 `npm.cmd` 명령을 사용하며 macOS/Linux에서는 `npm`으로 실행합니다.

```powershell
# package.json이 있는 frontend 폴더에서 실행
npm.cmd ci          # 다른 PC에서 처음 실행할 때
npm.cmd run dev
```

- [React 전체 흐름](http://127.0.0.1:5173/#/preview): 역할별 로그인·가입 또는 화면·상태 목록에서 시작합니다.
- [HTML 비교본](http://127.0.0.1:5173/html-reference.html#/preview): 전환 전 동작을 대조하는 별도 진입점입니다. 기존 소스를 보존했습니다.
- **구매자/판매자/관리자 시작**과 회원가입은 실제 계정 API를 호출합니다. **시연 시작**·화면 목록은 기존 예시 데이터를 사용합니다.
- 시연 화면 하단 **React 미리보기**에서 역할, 승인·등록 응답·사진 업로드·연결 오류 시나리오를 바꿀 수 있습니다. 실제 계정 모드에는 이 조작 도구가 없습니다.

```powershell
npm.cmd run build    # dist에 React와 HTML 비교본 생성
npm.cmd run preview  # 빌드 결과 확인
npm.cmd run lint     # Oxlint
npm.cmd test         # 도메인·라우팅·실제 인증 계약·취소/세션 회귀
```

ES 모듈을 사용하므로 파일 탐색기로 index.html을 직접 열지 않고 Vite로 실행합니다.

## 전체 흐름 통합 검증

2026-10-12 백엔드 `7dc28c7`과 격리 DB에서 가입·매장·승인·원단/사진·추천·예약·문의·프로필·AI 개발 제공자 흐름을 함께 검증했습니다. 프론트 365개·백엔드 474개 테스트, 실제 adapter 연속 시나리오 42항목과 HTTP 경계 15항목이 통과했습니다. 브라우저에서는 판매자 첫 진입부터 관리자 승인, 구매자 문의·예약, 판매자 수락·달력·수령 완료와 재고 반영을 확인했습니다.

추천 화면의 문의 연결과 문의 후 원래 검색/도안 화면으로 돌아가는 경로를 보완하고, 판매자·관리자 화면의 오래된 안내를 수정했습니다. 기존 로컬 DB 11개 모델의 전체 행은 작업 전후 동일했습니다. 자세한 범위와 제약은 [통합 검증 기록](docs/qa/integrated-flow-2026-10-12/README.md)에 있습니다. 팀 공용 배포 준비는 이 검증본에서 분리한 별도 브랜치·폴더에서 진행하며, 로컬 설정과 데이터를 복사하지 않습니다.

## 계정 API 연결

2026-10-11에 API 명세 v0.3과 인증 연동 당시 백엔드 main `9e65521ac1d3cb5fded0e9f7f15f76783c3bf8ca`를 대조하여 로그인·가입·내 정보·내 매장 조회 adapter를 추가했습니다. 화면 CSS와 기존 로그인 → 처리 → 완료/오류 흐름은 유지했습니다.

기본 요청은 `/api/v1`로 보내며, Vite 개발/preview 프록시가 `http://127.0.0.1:3000`으로 전달합니다. 같은 날 백엔드 `e177ea685a6588e39b58c75e04b513abd888785f`와 PostgreSQL을 로컬에서 실행하고, 실제 React 화면에서 구매자·판매자 가입과 로그인을 검증했습니다. 백엔드 테스트 **168개**, 실제 브라우저·DB 확인 **182개 항목**을 통과했습니다. 현재 PC의 재실행 방법과 검증 범위는 [로컬 백엔드 실행·검증 기록](docs/LOCAL_BACKEND_TEST.md)을 참고하세요.

다른 PC에서는 백엔드 저장소의 README에 따라 DB와 서버를 별도로 준비해야 합니다. 저장소에서 배포 API 주소는 확인되지 않았으며, GitHub 저장소 주소 자체는 API 서버 주소가 아닙니다.

주소가 달라지면 `.env.example`을 참고하여 `.env.local`에 설정하고 Vite를 다시 실행하세요.

```dotenv
VITE_API_BASE_URL=/api/v1
API_PROXY_TARGET=http://127.0.0.1:3000
```

배포 시에는 `/api` 역방향 프록시를 별도로 구성하거나 `VITE_API_BASE_URL=https://실제_API_호스트/api/v1`로 **빌드**해야 합니다. 다른 출처의 API를 직접 호출하면 백엔드 `CORS_ORIGIN`에 실제 프론트 주소가 필요합니다. 기본값 `http://localhost:5173`과 `http://127.0.0.1:5173`는 서로 다른 출처입니다. JWT 비밀키·DB 비밀번호는 프론트 환경변수에 넣지 않습니다.

- `POST /auth/signup`: 실제 `terms_agreed`·`privacy_agreed` 필드로 전송. 가입 후 자동 로그인하지 않고 기존 완료 → 로그인 흐름을 유지합니다.
- `POST /auth/login`: email/password만 전송. 응답의 실제 역할로 이동합니다. 판매자는 `hasStore=false`면 매장 입력 화면으로 이동하며, 승인 상태와 별도로 취급합니다.
- `GET /users/me`: 로그인 직후와 새로고침 복구 시 Bearer 토큰으로 계정 확인. 인증 복구에서는 매장이 있는 판매자의 `GET /stores/me`를 조회하며, 매장 관리 화면은 최신 매장 존재 여부를 다시 확인합니다.
- 토큰은 서버 `expiresIn`에 따라 만료되며, 탭의 sessionStorage에 토큰·만료 시각·API 주소만 저장합니다. 비밀번호는 저장하지 않습니다. 401과 로그아웃은 토큰을 제거하며, 서버에 없는 refresh/logout API를 호출하지 않습니다. 현재 서버 계약의 로그아웃은 발급된 토큰의 서버 폐기가 아닌 클라이언트 제거입니다.
- 구매자 원단 조회와 픽업 예약 요청·내역·취소, 판매자 예약 처리·대시보드 통계·픽업 달력·직접 원단 관리·사진·매장 등록/수정은 아래 후속 작업에서 연결했습니다. 관리자 조회·승인·거절, 구매자 도안 추천·조회와 판매자 AI 보조 등록 API도 연결했습니다. 문의 작성·목록·답변과 구매자·판매자 개인 프로필 수정도 후속 작업에서 연결했습니다. 실제 모드에는 시연용 계정·재고를 자동으로 넣지 않고, 미연동 저장은 성공 처리하지 않습니다. 기존 전체 흐름은 시연에서 계속 확인할 수 있습니다.

직접 확인: [실제 구매자 로그인](http://127.0.0.1:5173/#/auth/buyer/login?mode=live), [실제 판매자 가입](http://127.0.0.1:5173/#/auth/seller/signup?mode=live), [전체 화면·시연](http://127.0.0.1:5173/#/preview).

## 구매자 원단 조회 API 연결

2026-10-12 백엔드 main `7dc28c7`의 최신 명세·구현을 확인하고 `GET /fabrics`, `GET /fabrics/{id}`를 연결했습니다. 기존 화면 배치와 로그인 이후 탐색 흐름을 유지합니다.

- 홈: 서버에 최근 등록된 자투리 최대 4건을 표시합니다.
- 목록: 자투리/롤, 소재·두께·색상 필터를 서버에서 조회하며 전체 개수와 이전/다음 페이지를 표시합니다. URL의 검색어·정렬 조건도 전달하고 유지합니다.
- 상세: 실제 사진·매장 주소·설명·가격·치수와 예약/구매 가능량을 표시합니다. 없는 사진은 명시적인 빈 상태로 보여 줍니다.
- 로딩·빈 결과·잘못된 조건·404·연결 오류·재시도를 구분하고, 화면 이동/로그아웃 이후 늦게 도착한 응답은 무시합니다.
- 픽업 예약과 실제 추천·도안, 원단 문의 작성·조회 API는 아래 후속 작업에서 연결했습니다. 구매자의 모든 원단에 걸친 본인 문의 전체 목록은 서버 계약이 별도로 필요합니다.

로컬 백엔드에는 별도 검증용 가상 원단 25건을 준비했습니다. 실제 판매 상품이 아니며 계정·DB·이미지·비밀번호는 이 저장소에 포함하지 않습니다. 다른 PC에서는 본인의 백엔드 데이터로 조회합니다. 변경 내용과 실제 API·브라우저 확인 범위는 [원단 API 연동 검증](docs/qa/fabric-api-2026-10-12/README.md)을 참고하세요.

## 구매자 픽업 예약 API 연결

2026-10-12 백엔드 원격 main을 다시 확인했으며 `7dc28c7` 이후 새 커밋은 없었습니다. 기존 서버에 구현된 다음 API를 React에 연결했습니다. 화면 배치와 요청 → 접수 결과 → 예약 내역 → 취소 확인 흐름을 유지합니다.

- `POST /reservations`: 한국 시간대(+09:00) 희망 일정과 요청 수량을 전송합니다. 요청은 재고 확보가 아니며 판매자 수락 후 확보됩니다.
- `GET /reservations/me`, `GET /reservations/{id}`: 상태별 서버 페이지와 상세·픽업 매장 안내를 조회합니다. 판매 완료·삭제된 원단의 예약 이력도 원단 조회와 독립적으로 표시합니다.
- `POST /reservations/{id}/cancel`: 요청됨·수락됨 예약을 확인 화면에서 취소하고 서버 내역을 다시 읽습니다.
- 자투리 예약 금액은 응답에 없으므로 0원으로 표시하지 않습니다. 롤은 요청 당시 `estimated_price`를 사용합니다. 현재 매장 정보와 예약 당시 정보는 구분합니다.
- 중복·재고 부족·상태 변경·권한 오류를 처리하고, 전송 결과가 불확실한 경우 재전송 대신 내역 확인을 안내합니다. 화면 이탈·로그아웃 후 늦은 결과로 이동하거나 초안을 지우지 않습니다.

구매자 연동 당시에는 전용 가상 데이터에 판매자 API를 호출해 수락 후 취소·재고 회복 등을 확인했습니다. [예약 API 연동 검증](docs/qa/reservation-api-2026-10-12/README.md)은 당시 확인 범위를 보존하며, 판매자 화면 연결은 아래 후속 작업에서 진행했습니다.

## 판매자 예약 API 연결

백엔드 원격 main은 `7dc28c7`로 동일합니다. 기존 상태 탭·예약 목록·선택 상세와 확인 화면을 유지하여 다음 API를 연결했습니다.

- `GET /sellers/me/reservations`: 상태·원단·페이지 조건으로 받은 예약을 조회합니다. 목록에 없는 사진·거절 사유는 공용 예약 상세 API로 확인합니다.
- `POST /reservations/{id}/accept`: 구매자가 요청한 일시 그대로 수락합니다. 별도 일정 변경 UI는 추가하지 않았습니다.
- `POST /reservations/{id}/reject`: 공백을 제외한 1~255자 사유를 보내며 구매자가 상세에서 확인할 수 있습니다.
- `POST /reservations/{id}/pickup`: 실제 전달 후 확인 화면에서 수령 완료를 처리합니다. 수락된 예약의 판매자 취소도 기존 취소 API를 사용합니다.
- 처리 성공 후 서버 내역을 다시 읽고, 응답 유실·상태 충돌에는 중복 전송보다 현재 상태 확인을 안내합니다. 수령 완료·거절·취소된 예약을 다시 처리하지 않습니다.

판매자 목록에는 구매자 전화번호·원단 사진·거절 사유·판매 형태가 모두 포함되어 있지 않습니다. 제공된 닉네임과 요청 길이·nullable 금액을 사용하고, 상세 조회와 구분합니다. 실제 검증 범위와 증거는 [판매자 예약 API 검증](docs/qa/seller-reservation-api-2026-10-12/README.md)에 정리합니다. 대시보드 통계와 날짜별 달력은 아래 후속 작업에서 연결했습니다.

## 판매자 대시보드·픽업 달력 API 연결

2026-10-12 원격 백엔드 main을 다시 확인했으며 `7dc28c7` 이후 변경은 없습니다. 기존 통계 카드·두 열 배치·월별 달력과 예약 상세 이동을 유지했습니다.

- `GET /sellers/me/fabrics`: 게시 중·승인 대기·승인 거절·판매 완료별 `totalElements`를 집계합니다.
- `GET /sellers/me/inquiries`: 답변 대기(`WAITING`)·답변 완료(`ANSWERED`) 건수를 조회합니다. 통계에는 문의 내용이나 구매자 정보를 저장하지 않습니다.
- `GET /sellers/me/reservations?status=ACCEPTED`: 수락 내역의 모든 페이지를 읽은 뒤 한국 날짜별로 묶고 시간 순서로 표시합니다. 오늘·날짜 선택·월 이동·월 전체 조회와 예약 상세 이동을 지원합니다.

- 개인 닉네임과 연락처를 수정하면 현재 세션과 화면에 반영합니다. 빈 연락처는 null로 삭제합니다. 이메일·역할은 변경하지 않으며 개인 연락처는 매장 전화나 예약별 연락처와 다릅니다.
- 저장 응답이 유실되면 성공이나 실패를 단정하지 않고 입력을 보존한 채 서버 내용을 확인합니다. 문의 POST를 자동 재전송하거나 같은 내용의 목록 항목만으로 생성 결과를 확정하지 않습니다.

이번 검증은 **기존 개발 DB에 데이터를 추가하지 않고 별도의 전용 테스트 DB·루프백 API·별도 Vite 화면**에서 실행했습니다. 테스트 계정·비밀번호·DB 파일과 실행 설정은 프론트 저장소에 포함하지 않습니다. 실제 API/DB·실제 React 화면과 제어된 응답 유실 테스트의 범위는 [문의·프로필 검증](docs/qa/inquiry-profile-api-2026-10-12/README.md)에 구분합니다.

프론트 전체362개·lint·build, 격리된 백엔드55개·실제 HTTP40항목·adapter20항목과 최종 읽기 전용 SQL/GET16항목이 통과했습니다. 기존 개발 DB11개 모델의 전체 행 해시가 유지됐습니다. 실제 화면의 답변 수정·비공개 가림·프로필 저장·연락처 삭제·재로그인과 모바일을 확인했으며 앱 번들697.02kB 경고는 남습니다.

구매자 전체 본인 문의 목록, 문의 수정·삭제46~47, 이메일·비밀번호 변경은 이번에 연결한 기존 계약과 다릅니다. 해당 화면/API를 새로 제공하려면 [후속 계약](docs/API_FOLLOWUPS.md)을 합의해야 합니다.

## 데이터와 API 경계

- 기존 localStorage 키 yangju-loop-html-v1를 그대로 사용해 HTML에서 제출한 시연 기록을 유지합니다. HTML 비교본과 React는 같은 저장소를 공유합니다.
- 작성 중 폼은 서비스별 메모리 Map에 보존하며, 성공·명시적 취소·로그아웃·초기화에 맞춰 정리합니다. 새로고침하면 메모리 초안은 사라집니다. 비밀번호는 영구 저장하지 않습니다.
- 화면 목록의 상태 예시는 별도 메모리 서비스에서 동작합니다. 기존 시연 데이터를 바꾸지 않고, 전체 흐름 화면으로 돌아오면 원래 데이터로 복귀합니다.
- 실제 인증은 `react/services/live-api.js`로 분리했습니다. 시연은 `prototype/services/mock-api.js`를 유지하며 실제 토큰이나 계정 정보를 넘기지 않습니다. `mode=live/demo` 선택은 탭에 보존되고, 숫자 scenario와 화면 목록은 시연으로 열립니다.
- 예약 이력 정보(B1), 생성 응답 유실·사진 복구(B2), 예약 연락처(B3), 부가 기능 범위(B4)는 [후속 API 협의 사항](docs/API_FOLLOWUPS.md)을 확인합니다. 연결·검증한 기존 계약과 아직 확정하지 않은 요청안을 구분하며 현재 기능별 확인 범위는 위 각 절과 QA 기록을 기준으로 합니다.

## 검증과 다음 작업

계정 API는 [HTTP 계약 검증 기록](docs/qa/auth-api-2026-10-11/README.md)에 이어 [실제 로컬 서버·DB 검증](docs/qa/local-backend-2026-10-11/README.md)까지 완료했습니다. 해당 실제 검증에서는 네트워크 응답을 대체하지 않았습니다. 이후 업무 API 연결은 위 각 절에 누적했으며 팀 공용 배포 검증은 남아 있습니다. 제어된 실패·지연을 주입한 후속 테스트는 각각의 QA 기록에 별도로 표시합니다.

이 저장소에서 `npm test`, `npm run lint`, `npm run build`를 재현할 수 있습니다. 브라우저 QA 결과와 캡처는 검증 당시의 기록입니다. 문서에 나오는 워크스페이스 `.maintenance` 스크립트와 로컬 DB 실행 도구는 이 프론트 저장소에 포함되지 않으며, 팀 공용 브라우저 테스트 명령으로 옮기는 작업은 남아 있습니다.

전환 직후 빌드·lint·단위 테스트32개와 역할별 회귀, HTML 비교를 통과했습니다. 이후 관리자 스크린샷을 계기로 [배치 수정 당시](docs/qa/layout-polish-2026-10-11/README.md) 177개 경로·354회 렌더 및 관리자840개 스크롤 위치를 확인했습니다. 이는 당시의 검증 기록입니다.

원단 API 연결에 앞서 [이용자 관점 검토](docs/qa/user-perspective-2026-10-11/README.md)를 반영한 [UX/UI 수정](docs/qa/ux-fixes-2026-10-12/README.md)을 진행했습니다. 공통·구매자·판매자·관리자로 나누어 반영했으며 테스트108개, lint, 빌드와 주요 모바일·데스크톱 흐름을 확인했습니다. 확정 약관 문안과 판매자 승인 거절 후 공식 문의·재검토 절차는 준비 대기 상태입니다. 실제 업무 API 연결과 구분한 검증 범위는 수정 결과 문서를 참고하세요.

원단 조회 연결 당시에는 테스트126개, lint, 빌드 및 실제 HTTP19개를 통과했습니다. 브라우저 확인과 남은 연결 범위는 [원단 API 검증](docs/qa/fabric-api-2026-10-12/README.md)에 정리했습니다.
